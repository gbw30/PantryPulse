## Intended HTTP workflow

1. Read a committed planning-ready forecast and current operational source state.
2. Capture an authenticated, coherent immutable input package, with actual source
   references, versions, inventories, demand, confirmed supply and explicit policy,
   route, reserve and capacity settings. Do not trust client-provided snapshots as
   verified database state or silently supply unlimited capacities/zero reserves.
3. `POST /api/v1/scenarios`: bind package/policy and required transfer mode, freeze
   the 1–3-day planning window and explicit scenario controls; return 201.
4. `POST /api/v1/scenarios/{id}/plans`: submit the independently chosen method,
   expected scenario hash, intent and idempotency key; durable 202 if admitted.
5. `GET /api/v1/jobs/{id}` then `GET /api/v1/plans/{id}`: saved status and verified
   recommendations with source/destination/lot/product/quantity/arrival/use dates,
   shortage impacts, native solver status and disclosed assumptions.

Busy/unavailable workers use the shared queue/admission behavior. Reads never
compute. Retry/cancel remain durable and fenced. Changing mode creates a separate
scenario. Paired methods use the same frozen mode and feasible region.
