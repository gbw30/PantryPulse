**Data and behaviour (exact contracts; the API is the validator).**
- *Catalog:* `GET operational-catalog` → `{ sites, products, donors, data_sources }` (raw rows); selects show names; ids never typed by hand except "open receipt by id".
- *Demand history:* source (data source) + rows `{source_record_key, site_id, product_id, day, expected_revision|null, requested|null, fulfilled|null, unmet|null}`; ≤100 rows; empty quantity cells stay **null** ("not reported"), never 0. Inputs: CSV file (exact header set from `operations.py:301–310`, ≤60 kB) via `POST imports/demand/csv`, or JSON file/paste via `POST imports/demand`; a downloadable header-only CSV template; a client preview table before submit. Success `CommandResult.result` → `accepted_count`, rows with revision per site/product/day. Rejection is **atomic**: error `details` `{atomic, accepted_count: "0", rejected_count, errors: [{row_index, field, code}]}` → "No rows were saved. N rows rejected." + table (row shown 1-based, field, code in plain words with the code beside it). 409 `STALE_HISTORY_REVISION` per row → "This day changed since you loaded it; set expected revision to the current one."
- *Donation coverage:* rows `{site_id, product_id, day, complete, expected_revision|null}` via `POST imports/donation-coverage`; same feedback.
- *Receipts:* create `POST receipts` (`donor_id, site_id, source_id, source_record_key, received_at` ≤ now, `is_void`, lines `{line_key, product_id, quantity ≥1}`, `expected_revision: null`) → `{receipt_id, revision_id, revision, stock_changed: false}`; view `GET receipts/{id}` (revisions + lines + reconciliation); revise `POST receipts/{id}/revisions` with `expected_revision` = latest (409 `STALE_RECEIPT_REVISION`); post/reconcile `POST receipts/{id}/post|reconcile` with `revision_id`, per-line `declarations` (eligibility + expiry), `expected_versions` for each receiving site × product (from `GET inventory/...`), optional `supply_matches`/`supply_versions`, `reason`. Show "Stock changed" only when the response says so.
- *Expected supplies:* list `GET supplies`; create `POST supplies` → state `UNCONFIRMED`; confirm `POST supplies/{id}/confirmation` with `expected_arrival_at|null`, `outstanding_quantity`, `expected_inventory_version`, `expected_supply_version`, `cancel`, `reason`. Label: "Confirmed supply is an expected arrival, not on-hand stock."
- *Lot declaration:* `POST inventory/lots/{lot_id}/declarations` `{eligibility, expiry {kind, expires_on|null}, reason, expected_inventory_version}`.
- *Stock adjustment:* `POST inventory/sites/{s}/products/{p}/adjustments` `{changes: [{lot_id, delta ≠ 0}], reason, source_reference, expected_inventory_version}` → `StockAdjustmentResult` before/after per lot and versions.
- *Version conflicts:* every stock write sends the version the user saw. 409 → "Inventory changed since you loaded it (you saw version X). Reload, review and re-apply." with `Reload inventory`; the draft is kept; no automatic retry.
- *Idempotency:* one key per user intent, reused if the same submission is retried after a network failure; a new key after the user edits the form. Buttons disabled while pending.
- *Visitor:* `/data/inputs` shows "Presenter sign-in required to enter data" and no forms; `/data/inventory` lots are presenter-only reads too (401) → same explanatory state; no write controls ever render for visitors.

**States.** Checking session; visitor; loading catalog; empty catalog; form validation (client mirrors regex/length limits, server 422 field errors mapped back); atomic import rejection; 409 stale (history, receipt revision, inventory version, supply version); 401 session expired (drop to visitor, keep draft in memory); 403 origin; 413 too large; 503 backend unavailable; network failure (Retry keeps the idempotency key); success.

**Accessibility.** Every input labelled; errors linked via `aria-describedby` and announced in a polite live region once; focus moves to the error summary after a failed submit and to the result panel after success; dialogs trap and return focus; tables have captions with unit and version.

**Acceptance.** `data-input.spec.ts` (three widths): visitor sees no forms on either route; presenter CSV import success shows accepted count; JSON import with two bad rows shows "No rows were saved", both row numbers and codes, and nothing else changed; empty quantity cells reach the request body as `null`; receipt create → revise with stale revision shows 409 copy; post receipt sends `expected_versions` from the loaded snapshot; supply create → confirm; lot declaration and adjustment send the loaded `inventory_version` and render the 409 conflict state with Reload; double click sends one request (same Idempotency-Key); `expectNoSeriousA11yViolations` per width. `PP_RUN_CONNECTED=1` test: one CSV import, one receipt post and one adjustment against the isolated seeded API.
